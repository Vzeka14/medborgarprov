## 1. Как сейчас устроено

### 1.1. Где лежат вопросы и в каком формате

Вопросы лежат в `data/questions-01-04.json`, `data/questions-05-07.json`,
`data/questions-08-10.json`, `data/questions-11-13.json` — обычные JSON-массивы,
разбитые по диапазонам глав (только по историческим причинам именования файлов,
на код это не влияет). Плюс отдельные файлы с пояснениями по языкам:
`data/why-sv.json`, `data/why-en.json`, `data/why-ar.json` (русское пояснение
хранится прямо в вопросе, поле `why`, а не в отдельном файле — непоследовательно
по сравнению с sv/en/ar).

Формат одного вопроса (см. `data/questions-01-04.json:1-33`):

```json
{
  "id": "c1-01",
  "ch": 1,
  "kind": "fakta",
  "ref": "Landet Sverige, s. 5",
  "sv": { "q": "...", "o": ["...", "...", "...", "..."] },
  "ru": { "q": "...", "o": [...] },
  "en": { "q": "...", "o": [...] },
  "ar": { "q": "...", "o": [...] },
  "correct": 2,
  "why": "..."
}
```

`ch` — номер главы (число 1–13), жёстко привязан к экзамену
medborgarskapsprovet: коды глав — просто числа без пространства имён экзамена.

### 1.2. Как вопросы попадают в приложение: build-bank.mjs

`data/build-bank.mjs` — это сборочный скрипт, а не часть runtime-приложения:

- Построчно (`build-bank.mjs:2`) читает **все** файлы `data/questions-*.json`
  (жёстко: каталог `data`, без параметра, без понятия "какой экзамен").
- Склеивает их в один массив, подмешивает `why` из трёх файлов
  `data/why-{sv,en,ar}.json` (`build-bank.mjs:7-11`).
- Валидирует: дубликаты `id`, наличие всех 4 языков и 4 вариантов ответа у
  каждого, корректность `correct`, наличие `ref`, наличие переводов пояснения
  во всех 4 файлах и отсутствие "осиротевших" пояснений (`build-bank.mjs:13-36`).
- Пишет результат в **один** файл: `src/data/questions.json`
  (`build-bank.mjs:39-40`) — путь тоже захардкожен.

Скрипт запускается через `npm run bank` (`package.json`), который, в свою
очередь, автоматически вызывается перед `npm run dev` и `npm run build`
(`package.json` — скрипты `dev`/`build`). `src/data/questions.json` — сгенерированный
файл, не в git (`.gitignore:3`).

Приложение (`src/lib/exam.js:1`) импортирует этот единственный сгенерированный
файл статически: `import bank from '../data/questions.json'`. Никакого
runtime-выбора "какой банк подгрузить" нет — банк один, зашит в бандл на этапе
сборки.

### 1.4. Генерация экзамена и сид

Всё в `src/lib/exam.js`:

- `rng(seed)` (`exam.js:34-42`) — детерминированный ГПСЧ (mulberry32).
- `codeToSeed(code)` (`exam.js:57-64`) — хеширует буквенно-цифровой
  "код варианта" (например `K3F9A`) в числовой сид, чтобы один и тот же код
  всегда давал один и тот же тест.
- `newVariantCode()` (`exam.js:53-55`) — генерирует случайный 5-символьный код.
- `buildExam(code, size = EXAM_SIZE)` (`exam.js:92-120`) — по сиду:
  1. группирует банк по `ch`;
  2. пропорционально `CHAPTER_WEIGHT` набирает вопросы по главам;
  3. дополняет/обрезает до ровно `size`;
  4. перемешивает порядок вопросов и порядок вариантов ответа в каждом
     (`shuffleOptions`, `exam.js:75-86`) — при этом варианты ответа
     перемешиваются **на всех 4 языках синхронно** (`sv`, `ru`, `en`, `ar` —
     `exam.js:80-83`), что жёстко фиксирует ровно эти 4 языковых поля в
     объекте вопроса.
- Отдельно `newSeed()` (`exam.js:69-71`) — сид не по коду варианта, а просто
  случайное число, используется для "тренировочных" режимов (капитель /
  вся банка), которые не привязаны к шарибельному коду, а сохраняются в
  `localStorage`.
- `buildChapterPractice(seed, ch)` и `buildBankPractice(seed)`
  (`exam.js:136-148`) — тренировочные наборы: все вопросы главы или весь
  банк целиком, без пропорций/лимита размера.

Всё это не знает о существовании "экзамена" как понятия отдельно от банка —
функции напрямую замкнуты на импортированный `bank` (единственный, глобальный,
из `../data/questions.json`) и на константы модуля (`EXAM_SIZE`,
`CHAPTER_WEIGHT`, `CHAPTER_TITLE`), которые описывают конкретно
medborgarskapsprovet.

### 1.5. Языки (шведский/русский) — как устроены

Два независимых понятия языка, оба сейчас общие на весь сайт:

1. **Язык интерфейса самого приложения** (кнопки, подписи, тексты типа
   "Föregående", "Lämna in", описание правил на стартовом экране) — **не
   локализован вообще**. Всё это — литералы на шведском прямо в JSX
   (`src/App.jsx`, весь файл). Русский/английский/арабский текст в приложении
   встречается только как: (а) перевод самих вопросов/вариантов ответа/пояснений
   (переключатель "Översättning" на стартовом экране), и (б) несколько строк в
   футере/блоке поддержки, вручную продублированные на русском внутри шведского
   текста (`src/App.jsx:777-787`, `835`) — не через какой-либо словарь, а
   просто вписанный второй язык в ту же строку.
2. **Язык перевода вопроса** — управляется через `LANG_KEY` в `localStorage`
   (`medborgarprov:sprak`), значение одно из `LANGS = ['ru', 'en', 'ar']`
   (`src/App.jsx:17`, `22-25`). Это выбирает, какое из полей `q[lang]`
   показывать рядом со шведским текстом вопроса. Управляет только тем, что
   видно в `Exam`/`Practice`/`Result`/`PracticeResult`, не переводит
   интерфейс.

Строк интерфейса как отдельного словаря/файла **нет**. Нет `i18n`-библиотеки,
нет `locales/`, нет `t()`-функции — весь текст интерфейса живёт прямо в JSX на
шведском.

### 1.6. Роутинг

Роутинга нет вообще. Один `<div id="root">` (`index.html:13`), один компонент
`<App />` (`src/main.jsx`), внутри которого `useState('start')` переключает
"экран" (`screen`) между `'start' | 'exam' | 'result' | 'practice' |
'practiceResult'` через условный рендеринг (`src/App.jsx:38-190`). URL никогда
не меняется, нет `react-router` или аналога в зависимостях (`package.json`),
нет `<a href>` навигации между "страницами" сайта — только смена состояния.
Значит: нет отдельного URL ни для стартового экрана, ни тем более для
"какой это экзамен" — сайт физически не может обслуживать два экзамена
одновременно даже по разным путям, потому что путей не существует в принципе.

## 2. Что мешает второму экзамену

Конкретные места, которые предполагают ровно один экзамен:

1. **Единственный статический импорт банка.** `src/lib/exam.js:1` —
   `import bank from '../data/questions.json'`. Второй банк добавить рядом
   некуда: либо переписывать этот импорт, либо городить условия внутри
   одного модуля.
2. **`build-bank.mjs` собирает всё из одной папки в один файл.**
   Жёстко: `data/questions-*.json` → `src/data/questions.json`
   (`build-bank.mjs:2, 39-40`). Нет параметра "для какого экзамена", нет
   разделения по выходным файлам.
3. **Все параметры экзамена — константы модуля, не данные.** `EXAM_SIZE`,
   `EXAM_MINUTES`, `DEFAULT_PASS`, `CHAPTER_WEIGHT`, `CHAPTER_TITLE`
   (`src/lib/exam.js:3-28`) экспортируются как одиночные значения, а не как
   параметры функции/поля конфига. `buildExam` читает `CHAPTER_WEIGHT` и
   `CHAPTER_TITLE` из замыкания модуля, а не принимает их аргументом.
4. **Главы — просто числа 1–13.** `ch` в данных вопроса — число без
   пространства имён (`CHAPTER_WEIGHT`/`CHAPTER_TITLE` — объекты, ключи
   1–13). У jägarexamen главы — 16 штук со строковыми слагами
   (`artkannedom`, `vapenlagstiftning`, ...; см.
   `docs/jagarexamen-struktur.md`, раздел "Блок chapters для config.js").
   Простое сосуществование двух банков в одном `bank` массиве с числовым `ch`
   у одного экзамена и строковым `ch` у другого либо потребует конфликтующих
   схем, либо неявного тегирования вопроса "к какому экзамену он относится" —
   которого сейчас нет вообще ни в одном вопросе.
5. **`localStorage`-ключи не различают экзамен.** `KEY = 'medborgarprov:pagaende'`,
   `BANK_KEY = 'medborgarprov:bank'`, `chapterKey(ch)` без экзамена в ключе,
   `LANG_KEY = 'medborgarprov:sprak'` (`src/App.jsx:9-16`) — если открыть два
   экзамена на одном сайте (даже последовательно, в одной вкладке браузера),
   их сохранённый прогресс, язык перевода и незавершённый тест будут писаться
   в одни и те же ключи и затирать друг друга. `chapterKey(ch)` вдобавок
   ломается, если `ch` у двух экзаменов совпадает по значению (например,
   оба используют числа с 1), потому что в ключе нет ничего, что отличало бы
   экзамен.
6. **Список языков перевода жёстко привязан к формату вопроса.**
   `LANGS = ['ru', 'en', 'ar']`, `WHY_FIELD`, `WHY_LABEL` (`src/App.jsx:17-20`)
   — компонент `Exam`/`Practice`/`Result` обращается к `q[lang]` и
   `q[WHY_FIELD[lang]]` напрямую, ожидая, что у **любого** вопроса в системе
   есть поля `ru`, `en`, `ar`, `why`, `whyEn`, `whyAr`. Для jägarexamen по
   плану (см. `docs/jagarexamen-regler.md`, раздел 4) переводы не обязаны
   быть теми же тремя языками ни семантически (RU/AR там — не язык сдачи
   экзамена), ни, возможно, синтаксически.
7. **`build-bank.mjs` требует наличие en/ar у каждого вопроса под страхом
   падения сборки.** `build-bank.mjs:18-21` — цикл `for (const lang of LANGS)`
   с `LANGS = ['sv', 'ru', 'en', 'ar']` (`build-bank.mjs:6`) валидирует
   **любой** вопрос в системе на все 4 языка. Если у jägarexamen изначально
   будет только `sv` (как и написано в задаче — "сейчас только sv для нового
   экзамена"), сборка немедленно упадёт на первом же вопросе второго
   экзамена, если он попадёт в тот же проход валидации.
8. **Весь текст стартового экрана — про medborgarskapsprovet, вписан в общий
   компонент `Start`.** `src/App.jsx:200-349` — заголовок, факты о "реальном
   экзамене" (60 вопросов, 90 минут, 15 августа 2026, Stockholmsmässan),
   объяснение режимов "kapitel"/"hela frågebanken" — всё это текст ровно про
   один экзамен внутри единственного компонента `Start`, который рендерится
   при `screen === 'start'` без параметра "какой экзамен показываем".
9. **Нет роутинга/экрана выбора экзамена.** `screen` в `useState` —
   замкнутый список состояний одного прохождения теста
   (`'start'|'exam'|'result'|'practice'|'practiceResult'`), нет состояния
   "выбор экзамена" и нет URL, который отличал бы `/medborgarskap` от
   `/jagarexamen` — see раздел 1.6. Без роутинга нельзя ни дать прямую
   ссылку на конкретный экзамен, ни разделить их на уровне адресной строки.
10. **`Support`/`SiteFooter` — общие компоненты с текстом, не зависящим от
    экзамена, но и не абстрагированным в конфиг.** Не критично для второго
    экзамена по сути (текст поддержки универсален), но при выносе в общий
    "движок" его тоже придётся явно решить, где он живёт — в движке или
    в обёртке экзамена.
11. **`App.jsx` — один файл на 841 строку, где смешаны: движок (таймер,
    генерация, шитинг ответов) и контент medborgarskapsprovet (тексты,
    список глав для отображения, дефолтные значения).** Само по себе не
    "ломает" второй экзамен технически, но означает, что рефакторинг —
    это не добавление файла, а разрезание существующего файла на слои.

## 3. Предлагаемая структура

Дерево файлов после рефакторинга (наименования ориентировочные — там, где я не
уверен в конкретном имени, ниже в разделе 4/6 это отмечено явно):

```
data/
  medborgarskap/
    build-bank.mjs               # текущий data/build-bank.mjs, специализация не нужна,
                                   # просто переезжает в свою папку
    questions-01-04.json
    questions-05-07.json
    questions-08-10.json
    questions-11-13.json
    why-ar.json
    why-en.json
    why-sv.json
  jagarexamen/
    build-bank.mjs                # свой сборщик (или общий параметризованный, см. риски)
    questions-artkannedom.json    # и т.д. по слагам глав из jagarexamen-struktur.md
    ...

src/
  main.jsx
  styles.css
  site.config.js                  # донаты и т.п. — как есть, не экзамен-специфично

  data/
    medborgarskap/
      questions.json               # сгенерированный build-bank выхлоп, было src/data/questions.json
    jagarexamen/
      questions.json               # сгенерированный, изначально только sv

  engine/                          # общий движок — НЕ знает, какой экзамен крутит
    exam.js                        # buildExam/scoreExam/shuffle/rng и т.п.,
                                   # но принимает bank + config аргументами,
                                   # а не импортирует их сам
    storage.js                     # обёртка над localStorage с namespacing по examId,
                                   # заменяет текущие захардкоженные ключи в App.jsx
    App.jsx                        # текущие компоненты Exam/Result/Practice/PracticeResult/Sheet,
                                   # параметризованные конфигом экзамена, без текста конкретного
                                   # экзамена внутри

  exams/
    medborgarskap/
      config.js                    # id, EXAM_SIZE, EXAM_MINUTES, DEFAULT_PASS,
                                   # CHAPTER_WEIGHT, CHAPTER_TITLE, LANGS, pass-опции, тексты Start

  routes/                          # ИЛИ прямо в App верхнего уровня — см. риски/открытые вопросы
    Home.jsx                       # экран выбора экзамена, /
    ExamPage.jsx                   # обёртка, которая берёт config по параметру роута
                                   # и рендерит engine/App с этим конфигом

  jagarexamen-struktur.md          # как есть
  refactor-plan.md                 # этот файл
```

Роуты: `/` — экран выбора экзамена, `/medborgarskap` — текущий сайт как есть
(под новым URL), `/jagarexamen` — новый экзамен. Технически это означает
добавление `react-router-dom` (или аналога) в зависимости — сейчас в
`package.json` роутера нет вообще (раздел 1.6), и это единственная новая
рантайм-зависимость, которую подразумевает целевая схема.

**Что не проектирую детально здесь:** финальные имена файлов внутри
`engine/`, точный API `config.js` (не видел, требует ли UI j
ägarexamen что-то, чего нет у medborgarskapsprovet — например, чтения из
15 языков вместо 3, — не выяснено, см. раздел 4 и открытые вопросы ниже).

## 4. Порядок шагов

Каждый шаг должен оставлять сайт рабочим (`npm run dev`/`build` проходят,
текущий medborgarskapsprovet отвечает как раньше).

### Шаг 1. Namespacing localStorage без смены структуры кода

Что меняется: ключи `KEY`, `chapterKey`, `BANK_KEY`, `LANG_KEY` в
`src/App.jsx:9-16` получают префикс с id экзамена (`medborgarprov:medborgarskap:...`
или похоже). Код и файлы больше нигде не двигаются.

Что может сломаться: у пользователей, у которых уже есть сохранённый
незавершённый тест в старом ключе `medborgarprov:pagaende`, прогресс "исчезнет"
(новый ключ, старый не читается) — это разовая, безвозвратная потеря
локального состояния у вернувшихся пользователей. Нужно решить: смириться
(состояние и так эфемерное, тест можно начать заново) или написать
одноразовую миграцию ключей при старте.

Как проверить: пройти тест наполовину, сохранить, перезагрузить страницу,
убедиться что "Fortsätt" предлагает продолжить с тем же вариантом; проверить
то же для тренировки по главе и по всей банке.

### Шаг 2. Выделить движок из App.jsx, не трогая поведение

Что меняется: `src/lib/exam.js` перестаёт статически импортировать
`../data/questions.json`; `buildExam`, `buildChapterPractice`,
`buildBankPractice`, `chapterCounts`, `scoreExam` начинают принимать банк и
параметры (`size`, `chapterWeight`, `chapterTitle`) аргументами вместо чтения
констант модуля. `EXAM_SIZE`/`EXAM_MINUTES`/`DEFAULT_PASS`/`CHAPTER_WEIGHT`/
`CHAPTER_TITLE` переезжают в `src/exams/medborgarskap/config.js`, и `App.jsx`
передаёt их в вызовы. Сам `App.jsx` пока остаётся один файл, экзамен
по-прежнему только один — просто данные конкретного экзамена больше не
зашиты внутрь `exam.js`.

Что может сломаться: любое место, которое неявно рассчитывало на порядок
вычисления констант модуля (например, `bankSize = bank.length` на верхнем
уровне модуля, `exam.js:30`, — при переходе на параметр это должно стать
функцией `bankSize(bank)` или вычисляться в компоненте). Сид/генерация не
должны измениться по результату — если параметры те же, тест на тот же код
варианта должен выдавать точно тот же набор вопросов, что и до рефакторинга.

Как проверить: сгенерировать тест по конкретному коду варианта **до**
рефакторинга (записать список id вопросов и порядок вариантов ответа),
повторить **после** рефакторинга с тем же кодом — списки должны совпасть
побайтово. Это самая важная регрессионная проверка всего рефакторинга
(см. также раздел 5, "сид").

### Шаг 3. Разделить данные и сборку по экзаменам (только medborgarskap физически перемещается)

Что меняется: `data/questions-*.json`, `data/why-*.json`, `data/build-bank.mjs`
переезжают в `data/medborgarskap/`; выход переезжает в
`src/data/medborgarskap/questions.json`. `package.json`-скрипт `bank`
обновляется на новый путь (или добавляется параметризация, если уже на этом
шаге вводится второй сборщик под jägarexamen — решить при реализации, оба
варианта совместимы с "сайт остаётся рабочим" на этом шаге, если trogged
только пути одного существующего экзамена).

Что может сломаться: `.gitignore:3` (`src/data/questions.json`) должен
обновиться на новый путь, иначе сгенерированный файл может случайно попасть
в git. Любой прямой импорт вида `from '../data/questions.json'` в коде
(на данный момент только `src/lib/exam.js:1`) должен быть обновлён.

Как проверить: `npm run bank && npm run build` проходят без ошибок,
`dist/` содержит тот же набор вопросов (сверить количество/контрольную
сумму с состоянием до переезда).

### Шаг 4. Ввести конфиг экзамена как формальный контракт + вынести контент Start

Что меняется: `src/exams/medborgarskap/config.js` формализуется (id, размеры,
лимиты, главы, языки, опции проходного балла — переносится
`[42, 45, 48, 52, 54]` из `App.jsx:251`). Текст стартового экрана
(`src/App.jsx:200-349`) выносится в `src/exams/medborgarskap/StartContent.jsx`
или аналог, специфичный для этого экзамена. `App.jsx` (движок) принимает
конфиг и контент-компонент как входные параметры вместо того, чтобы содержать
их сам.

Что может сломаться: любая логика в `Start`, которая была неявно завязана на
конкретные тексты (например, `EXAM_SIZE`/`bankSize` подставлялись в текст
через шаблонные строки, `src/App.jsx:205-207, 296-298`) — при выносе текста
в отдельный компонент эти значения нужно явно прокинуть параметрами, а не
скопировать текст с захардкоженными числами.

Как проверить: визуальное сравнение стартового экрана до/после (тот же
текст, те же значения по умолчанию в селектах); полный прогон теста от
старта до результата.

### Шаг 5. Добавить роутинг и экран выбора экзамена

Что меняется: добавляется зависимость-роутер, `/` получает новый компонент
"выбор экзамена", `/medborgarskap` рендерит существующий движок с конфигом
medborgarskap, резервируется `/jagarexamen` (может временно вести на
заглушку "скоро"). `vite.config.js` не должен требовать изменений для
поддержки клиентского роутинга при статичном хостинге на этом шаге —
GitHub Pages отдаёт `404.html`/фолбэк только если это настроено отдельно
(см. риски, раздел 5) — на моменте написания этого документа в репозитории
такого файла нет, вопрос как решать SPA-фолбэк на GitHub Pages остаётся
открытым и подробно расписан в разделе 5.

Что может сломаться: старые ссылки на корень сайта (`/`) — раньше это сразу
был стартовый экран medborgarskapsprovet, после этого шага там будет экран
выбора. Внешние ссылки/закладки, которые вели на `/` ожидая сразу тест,
перестанут вести прямо на тест. Обновление прямой ссылки в README/соцсетях
на `/medborgarskap`, если такие есть, — не проверялось, не входит в этот
рефакторинг-план как код, но стоит отметить пользователю отдельно.

Как проверить: переход по `/`, `/medborgarskap` напрямую (в т.ч. hard refresh
на `/medborgarskap`, чтобы проверить, что GitHub Pages не отдаёт 404 при
прямом заходе на подпуть — это конкретно нужно тестировать на реальном
деплое, не только `npm run dev`, потому что dev-сервер Vite и статический
хостинг обрабатывают несуществующие пути по-разному).

### Шаг 6. Добавить данные и конфиг jägarexamen, включить второй маршрут

Что меняется: `data/jagarexamen/` наполняется вопросами (только `sv`, как
указано в задаче), `src/exams/jagarexamen/config.js` — по блокам из
`docs/jagarexamen-regler.md` (раздел 6) и `docs/jagarexamen-struktur.md`

`timeLimitMin: 60`, `passingScore: 60`, 16 глав со слагами. `/jagarexamen`
перестаёт быть заглушкой.

Что может сломаться: `build-bank.mjs`-валидация "каждый вопрос должен иметь
sv+ru+en+ar" (`build-bank.mjs:18-21`) должна перестать применяться к

en/ar/ru (см. пункт 7 раздела 2). Это явно требует решения на уровне сборки:
либо параметризовать `LANGS` для валидации per-экзамен, либо у jägarexamen

остальные опциональными по конфигу экзамена, а не глобально по коду.

Как проверить: `npm run bank` не падает при отсутствии ru/en/ar у вопросов
jägarexamen; полный проход теста jägarexamen от старта до результата;
проверка, что medborgarskapsprovet по-прежнему требует все 4 языка (это
поведение не должно тихо ослабнуть заодно).

## 5. Риски

- **Сид генерации (самый серьёзный риск).** `buildExam` использует
  `codeToSeed(code)` (`exam.js:57-64`) и порядок обхода `Object.keys(pools)`
  (`exam.js:102`) — порядок ключей объекта в JS для строковых числовых ключей
  **гарантированно** идёт по возрастанию числа, но если `ch` станет строкой
  (как у jägarexamen — слаги вида `artkannedom`), порядок ключей вместо этого
  станет порядком **вставки**, то есть будет зависеть от порядка вопросов в
  исходном банке. Любая перестановка порядка глав или порядка загрузки файлов
  вопросов при рефакторинге (шаг 2/3) рискует **незаметно** поменять
  результат `buildExam` для существующих кодов вариантов medborgarskapsprovet,
  даже если сами данные не менялись. Раньше выданные пользователями коды
  вариантов (`K3F9A` и т.п., например, скопированные в переписке/соцсетях)
  после рефакторинга должны продолжать генерировать тот же набор вопросов —
  иначе "поделиться вариантом" перестаёт работать ретроактивно. Это нужно
  зафиксировать регрессионным тестом (см. шаг 2) до любого изменения порядка
  файлов данных.
- **Ссылки на варианты теста.** Если у сайта есть механизм передачи кода
  варианта через URL (не найден в текущем коде — код варианта сейчас
  вводится вручную в поле, `src/App.jsx:270-283`, а не через query-параметр),
  то этот риск не актуален. Но стоит перепроверить, не передают ли
  где-то код варианта через URL — не просматривался внешний код/лендинги,
  на которые могли бы ссылаться такие URL.
- **Аналитика GoatCounter.** Подключена единственным `<script
  data-goatcounter=...>` в `index.html:15`, без единого явного вызова из
  JS-кода (`window.goatcounter...` нигде не встречается в `src/`) — то есть
  это чистый pageview-трекер, реагирующий на смену `document.location`. Раз
  роутинга нет, при переходе между "экранами" `screen` URL не менялся — то
  есть **GoatCounter сейчас видит ровно один просмотр страницы на всю сессию
  теста**, независимо от того, сколько экранов внутри API прошло. После
  введения роутинга (шаг 5) поведение поменяется: переходы между `/`,
  `/medborgarskap`, `/jagarexamen` начнут быть настоящими сменами URL. Нужно
  явно решить, должен ли GoatCounter в SPA-режиме отслеживать переходы между
  роутами как отдельные просмотры (потребует ручного вызова
  `window.goatcounter.count(...)` при смене маршрута) — иначе после
  рефакторинга аналитика станет **менее** детальной, а не более, если явно
  этим не заняться.
- **Деплой на GitHub Pages.** `.github/workflows/deploy.yml` собирает
  `dist/` и публикует как статику. Текущий сайт — SPA без единого другого
  маршрута, поэтому вопрос "что происходит при прямом заходе на несуществующий
  путь" никогда не возникал. После добавления клиентского роутинга (шаг 5)
  прямой заход или обновление страницы на `/medborgarskap` или `/jagarexamen`
  отправит запрос на сервер GitHub Pages за файлом с таким путём, которого не
  существует — GitHub Pages по умолчанию отдаёт 404, если нет
  `404.html`-фолбэка, настроенного на редирект в `index.html`. В репозитории
  такого файла сейчас нет. Это нужно либо добавить (`404.html` с
  redirect-скриптом или копия `index.html`), либо выбрать hash-роутинг
  (`/#/jagarexamen`), который не требует серверной поддержки путей вообще —
  сам не определился, какой вариант предпочтителен, это открытый вопрос к
  автору, а не то, что можно решить, просто прочитав код.
- **`vite.config.js` — `base`.** `base: process.env.VITE_BASE ?? '/'`
  (`vite.config.js:8`) — один общий базовый путь для всего сайта, не для
  каждого экзамена отдельно. Это должно продолжать работать как есть (все
  роуты — под одним base), но при добавлении роутера нужно убедиться, что
  роутер сконфигурирован с тем же `base`, иначе относительные ссылки между
  `/`, `/medborgarskap`, `/jagarexamen` разъедутся при деплое не в корень
  домена.
- **`build-bank.mjs`-валидация языков, применённая ко всем экзаменам сразу.**
  Уже разобрано в разделе 2 (пункт 7) и разделе 4 (шаг 6) — если сборщик не
  разделить по экзаменам, добавление jägarexamen с одним `sv` немедленно
  ломает `npm run bank`, то есть ломает **весь** сайт, а не только новый
  экзамен, при первом же коммите вопросов jägarexamen. Это не гипотетический
  риск, а гарантированный сбой сборки, если явно не поменять валидацию.
- **Смешение `ch` как числа и `ch` как строки в одном движке.** Разобрано в
  разделе 2 (пункт 4). Если тип `ch` не унифицировать (например, оба экзамена
  на строковые слаги, с миграцией существующих числовых `ch` у
  medborgarskapsprovet), любой код в движке, который сравнивает `ch` через
  `Number(ch)` (как сейчас в `exam.js:138`, `buildChapterPractice`) может
  тихо перестать находить вопросы одного из двух экзаменов.

## Как реализация разошлась с планом

Ниже — только те решения, где фактическая реализация отличается от того,
что написано выше, и почему. Не список всего сделанного (для этого —
`git log` и `README.md`, раздел «Архитектура»).

- **Тип `ch` у medborgarskap не меняли на строку.** Раздел 5 («Смешение
  `ch` как числа и как строки») рассматривал в том числе миграцию
  medborgarskap на строковые слаги, чтобы унифицировать с jägarexamen.
  Вместо этого числовой `ch` (1–13) остался как есть, а движок
  (`src/lib/exam.js`) научился сравнивать/группировать `ch` через
  нормализацию к строке (`chKey()`) везде, где это происходит. Тип
  перестал иметь значение для движка — конкретным экзаменам не нужно
  подстраиваться друг под друга.
- **Банк канонизируется сортировкой по `id` внутри движка, при каждом
  вызове** (`canonicalBank()` в `src/lib/exam.js`), а не один раз на
  этапе сборки данных. Раздел 5 («Сид генерации») описывал риск как
  зависимость результата от порядка `Object.keys()`/порядка вставки, но
  не фиксировал конкретный механизм защиты. Выбранный вариант — гарантия
  не зависит от того, откуда вызывающий код взял `bank` и в каком
  порядке тот собран, а не только от того, что сборщик сделал всё
  правильно один раз.
- **Порядок глав — из `config.chapters` (явный список), а не из
  канонизации банка.** Отдельно от сортировки банка по `id`: порядок, в
  котором движок обходит главы при пропорциональном наборе вопросов
  (`buildExam`), берётся из порядка элементов в `config.chapters`, а не
  выводится из данных. Раздел 3 предполагал вынос списка глав в конфиг,
  но не уточнял, что именно порядок этого списка станет источником
  истины для порядка обхода.
- **`shuffleOptions()` работает от полей самого вопроса, а не от
  `config.requiredLangs`.** Ни план, ни раздел 4 (шаг 6) не
  предусматривали этот выбор явно — в момент написания плана
  `shuffleOptions()` ещё не был параметризован по языкам вообще (раздел
  2, пункт 6, описывает риск как хардкод `LANGS` в `App.jsx`, не в
  `exam.js`). При реализации (последний шаг) источником списка языков
  выбраны сами поля вопроса (`{ q, o }`-подобная форма), а не
  `requiredLangs` из конфига — `requiredLangs` описывает нижнюю границу
  (что обязано быть), а не то, что реально есть у конкретного вопроса;
  вопрос может легально иметь языковое поле сверх `requiredLangs`, и
  ориентация на конфиг оставила бы такое поле неперемешанным.
- **Namespacing `localStorage`-ключей (раздел 4, шаг 1) не сделан.**
  План предлагал префиксовать `KEY`/`chapterKey`/`BANK_KEY`/`LANG_KEY`
  id экзамена, с оговоркой, что это разово стирает прогресс уже
  вернувшихся пользователей. Решение — не жертвовать существующим
  прогрессом medborgarskap: ключи (`medborgarprov:pagaende`,
  `medborgarprov:kapitel:<ch>`, `medborgarprov:bank`,
  `medborgarprov:sprak`) остались ровно такими же во всех шагах.
  Коллизия, которую это откладывает (раздел 2, пункт 5 — два экзамена с
  общими ключами затрут прогресс друг друга), реальна и не устранена;
  она встанет, когда у jägarexamen появится собственный работающий
  экран прохождения теста — см. README, раздел «Архитектура», шаг
  добавления экзамена.
- **Роутер — не `react-router-dom`, а собственная реализация
  (`src/router.jsx`, History API).** Раздел 3 и раздел 4 (шаг 5) считали
  `react-router-dom` «единственной новой рантайм-зависимостью, которую
  подразумевает целевая схема». Для ровно трёх статичных маршрутов без
  вложенности и параметров вес библиотеки показался неоправданным —
  написан свой минимальный роутер вместо неё; новых рантайм-зависимостей
  не добавилось вообще.
- **Нет общего `engine/App.jsx` + `exams/<id>/StartContent.jsx`, как
  предлагал раздел 3.** Целевое дерево описывало разделение на
  экзамен-агностичный UI-движок (принимает конфиг и контент-компонент
  параметрами) и отдельный компонент текста стартового экрана на
  экзамен. По факту весь UI medborgarskap (стартовый экран, прохождение,
  результат — все состояния бывшего `App.jsx`) переехал одним файлом,
  `src/exams/medborgarskap/MedborgarskapExam.jsx`, без разбора на
  движок+контент. У третьего экзамена не будет «бесплатного» UI от
  переиспользования общего движка — см. README, раздел «Архитектура».
